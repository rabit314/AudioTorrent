# AudioTorrent (AudioTorrent) — Codebase Bug Audit & Fix Planning

## 1. Executive Summary & Architecture Overview

AudioTorrent (AudioTorrent) is an Android audiobook streaming and progressive read-along application targeting Android API 26+ (Android 8.0 Oreo through Android 15/16). It integrates four primary subsystems:
1. **Torrent Engine & Streaming Bridge**: `TorrentEngine.kt`, `StreamSession.kt`, `StreamServer.kt`, `PublicWebseedBridge.kt` interfacing native `libtorrent4j` (C++ libtorrent SWIG JNI) and loopback HTTP/1.1 range servers to ExoPlayer.
2. **Audio Playback Subsystem**: `PlaybackController.kt`, `PreparedPlayback.kt`, and `AudioTorrentMediaService.kt` coordinating Jetpack Media3 (ExoPlayer), Android `MediaSessionService`, SQLite persistence (`playback_state`, `playback_history`), and speed/audio boost controls.
3. **Read-Along, Speech Recognition & Text Alignment**: `AudioWindowDecoder.kt`, `Pcm16kResampler.kt`, `WhisperEngine.kt` (JNI binding to `whisper.cpp`), `NarrationMatcher.kt`, `PacedTimingEngine.kt`, `PageTextManager.kt`, and `ReadAlongRepository.kt`.
4. **Catalog & Ebook Data Acquisition**: `AudioBookBayClient.kt`, `LibriVoxClient.kt`, `GutenbergClient.kt`, `ZLibraryClient.kt`, `BookIdentityResolver.kt`, and SQLite database `TorrentDatabase.kt`.

A rigorous static analysis, cross-subsystem trace evaluation, and crash log analysis (corroborating historical run reports `plan017-intermittent-native-crash.log`, `plan019-final-native-crash.log`, and live test runs) identified **10 critical and latent bugs** spanning native memory corruption, concurrency deadlocks, main-thread disk I/O, audio decoding/resampling edge cases, and UI synchronization issues.

### BUG-001: Native Memory Use-After-Free & JNI Modified UTF-8 Process Abort in TorrentEngine
- **Category**: Native Memory / JNI Lifecycle / Signal Crash
- **Severity**: Critical (P0) — Fatal Signal 11 (SIGSEGV) and Signal 6 (SIGABRT) terminating application process.
- **Source Locations**:
  - `app/src/main/java/com/example/audiotorrent/torrent/TorrentEngine.kt`: Lines 556–558, 606–624 (`refresh()`, `readFiles()`)
  - `app/src/main/java/com/example/audiotorrent/stream/StreamSession.kt`: Lines 30–36 (`files = info.files()`)
- **Evidence from Logcat & Crash Dumps**:
  - `app/build/plan019-final-native-crash.log:17195`: SIGSEGV (signal 11) in `org.libtorrent4j.FileStorage.filePath -> libtorrent_jni.file_storage_file_path` during `PreparationLeaseTest` concurrent cleanup.
  - `app/build/plan017-intermittent-native-crash.log:46-50`:
    `Abort message: 'JNI DETECTED ERROR IN APPLICATION: input is not valid Modified UTF-8: illegal start byte 0x9d string: '\235\332o' in call to NewStringUTF from java.lang.String org.libtorrent4j.swig.libtorrent_jni.torrent_info_name'`
- **Root-Cause Analysis**:
  In libtorrent4j SWIG bindings:
  1. `TorrentHandle.torrentFile()` returns a `TorrentInfo` Java wrapper pointing to libtorrent C++ `std::shared_ptr<const torrent_info>`.
  2. `TorrentInfo.files()` returns a `FileStorage` wrapper where `cMemoryOwn = false` (a borrowed, unmanaged C++ reference `const file_storage&`).
  3. In `TorrentEngine.refresh()`, which runs on a polling loop every 1000–3000 ms, lines 556–558 repeatedly call `handle.torrentFile()` and `readFiles(hash, handle, info)`. Inside `readFiles()`, line 614 repeatedly calls `storage.filePath(index)` for all files in the torrent.
  4. When `TorrentEngine.removeTorrent(hash)` or `shutdown()` is called, Kotlin executes `session.remove(handle)`. Libtorrent posts an asynchronous deallocation job to its internal network thread.
  5. The Kotlin `metadataLock` only synchronizes Kotlin threads; it does not block libtorrent's internal C++ threads. When libtorrent deallocates the C++ `torrent` object and its `torrent_info`, any Java `FileStorage` or `TorrentInfo` handle borrowed during or immediately before removal is left holding a dangling C++ pointer.
  6. When `storage.filePath(index)` reads through the dangling pointer:
     - If the memory page has been unmapped by the OS allocator, ART crashes with SIGSEGV (signal 11).
     - If the memory page has been recycled with arbitrary heap data, SWIG passes arbitrary raw bytes (`0x9d 0xda 0x6f...`) to `env->NewStringUTF(...)`. ART validates standard Modified UTF-8, fails on non-standard bytes, and executes `Runtime::Abort()`, killing the app with SIGABRT (signal 6).
  7. In `StreamSession.kt`, `info` and `files = info.files()` are stored as long-lived fields on the lease, keeping borrowed C++ pointers alive across arbitrary streaming lifecycles even after handle invalidation.

- **Worked Example**:
  - *Input*: User is listening to an audiobook track while another torrent in the library finishes or is removed via "Delete torrent".
  - *Observed Execution*: Polling loop in `refresh()` calls `getLiveHandle(hash)`. Handle is valid for a few microseconds while C++ teardown is in flight. `info.files().filePath(0)` executes while C++ memory is freed -> `SIGSEGV in FileStorage.filePath` or `SIGABRT: illegal start byte 0x9d`.
  - *Expected Execution*: File metadata is cached in immutable Kotlin memory upon torrent addition/metadata alert. `refresh()` never queries borrowed C++ `file_storage` during polling.

- **Remediation Plan & Kotlin Diff**:
  1. Cache immutable file metadata (`TorrentMetaSnapshot`: list of relative paths, names, file sizes, audio flags) in memory as soon as metadata is received or when added from bytes/database.
  2. In `refresh()`, NEVER call `handle.torrentFile()` or `info.files()`. Only call `handle.fileProgress()` (which returns a primitive `LongArray`) and status metrics.
  3. In `StreamSession.kt`, replace the borrowed `info` and `files` objects with primitive values (`fileOffset`, `fileSize`, `pieceLength`, `numPieces`).
  4. Guard `StreamSession.awaitRange` with explicit `handle.isValid` checks.

```kotlin
// In TorrentEngine.kt
```

### BUG-002: Connection Accept Deadlock via Pre-Accept Semaphore & Keep-Alive in PublicWebseedBridge
- **Category**: Concurrency / Streaming Deadlock
- **Severity**: High (P1) — Webseed downloads freeze completely when concurrency limit is reached.
- **Source Location**: `app/src/main/java/com/example/audiotorrent/torrent/PublicWebseedBridge.kt`: Lines 47–60, 66–105
- **Root-Cause Analysis**:
  1. `PublicWebseedBridge` uses `permits = Semaphore(4)` to bound concurrency against upstream Archive.org endpoints.
  2. In `register()`, the server accept loop executes:
     ```kotlin
     while (isActive) {
       permits.acquire()
       val client = try { socket.accept() } catch (_: IOException) { permits.release(); break }
       clients += client
       scope.launch {
         try { client.use(::serve) } catch (_: IOException) {}
       }.invokeOnCompletion { runCatching { client.close() }; clients -= client; permits.release() }
     }
     ```
     `permits.acquire()` is called BEFORE `socket.accept()`.
  3. In `serve(socket)`, the HTTP response includes `Connection: keep-alive\r\n\r\n`. After sending a range chunk, `serve` continues in a loop: `val request = line(input) ?: return` with `socket.soTimeout = 15_000`.
  4. When 4 concurrent connections finish their range requests, they sit idle in HTTP keep-alive, waiting up to 15 seconds for another request.
  5. Because those 4 coroutines have not exited, `invokeOnCompletion` has not run, and 0 permits remain.
  6. The accept loop suspends on the 5th iteration at `permits.acquire()`. Consequently, `socket.accept()` is NOT called.
  7. When libtorrent attempts to open a 5th connection to download a new piece, the incoming TCP connection sits in the OS socket backlog (backlog size is set to only 8). If libtorrent times out or if the backlog fills, downloads stall indefinitely.
  8. Furthermore, `roots` in line 37 prepends `"https://archive.org/download/"` before `origins`. The `download/` endpoint on Archive.org always issues 302 redirects to specific cluster nodes (e.g. `ia801600.us.archive.org`), forcing an extra HTTP roundtrip on every chunk and failing if Archive.org redirects to HTTP (which `PublicCatalogHttp` rejects as an "Insecure catalog redirect").

- **Worked Example**:
  - *Input*: LibriVox audiobook download begins. Libtorrent opens 4 parallel webseed connections to fetch pieces 0–3.
  - *Observed Execution*: 4 chunks arrive. Connections stay open waiting for pipelined requests. Libtorrent opens a 5th connection for piece 4. Accept loop is blocked on `permits.acquire()`. Socket times out after 15 seconds -> Swarm stalls on piece 4.
  - *Expected Execution*: New TCP connections are accepted immediately. Concurrency permits gate upstream HTTP data transfer, not TCP connection acceptance.

- **Remediation Plan & Kotlin Diff**:
  1. Move `permits.withPermit` inside `serve()` around `transfer()`, leaving `socket.accept()` unblocked.
  2. Send `Connection: close` on range responses, or close idle sockets after 1000 ms of inactivity rather than holding keep-alive for 15 seconds.
  3. Place direct `origins` ahead of the generic `download/` redirector.
  4. Increase server socket backlog from 8 to 64.

```kotlin
// In PublicWebseedBridge.kt
val roots = (origins + listOf("https://archive.org/download/")).distinct().map { ... }

// In server accept loop:
if (server == null) {
  val socket = ServerSocket(0, 64, InetAddress.getByName("127.0.0.1"))
  server = socket
  scope.launch {
    while (isActive) {
      val client = try { socket.accept() } catch (_: IOException) { break }
      clients += client
      scope.launch {
        try {
          client.use { serve(it) }
        } catch (_: IOException) {
        } finally {
          clients -= client
        }
      }
    }
  }
}

// In serve(socket): gate the upstream transfer with permit:
try {
  if (parts[0] == "HEAD") ready()
  else {
    val wanted = PublicSeedRange(recording!!.origins, path!!, size, from, to)
    permits.withPermit {
      transfer(wanted, output, ready)
    }
  }
  output.flush()
} finally {
  // Always close connection after range transfer to prevent idle permit exhaustion
  return
}
```

### BUG-003: Unsynchronized Concurrent Access to `deadlinePieces` and `tailPieces` in StreamSession
- **Category**: Concurrency / Thread Safety
- **Severity**: High (P1) — `ConcurrentModificationException` or CPU 100% hash loop during seeking.
- **Source Location**: `app/src/main/java/com/example/audiotorrent/stream/StreamSession.kt`: Lines 35–37, 92–126 (`armWindow()`)
- **Root-Cause Analysis**:
  1. `StreamSession` maintains `private val deadlinePieces = HashSet<Int>()` and `private val tailPieces = HashSet<Int>()`.
  2. `lastWindowPos` is a non-volatile `var lastWindowPos = -1L`.
  3. When ExoPlayer seeks, it closes the previous HTTP range request and rapidly opens a new one. In `StreamServer.kt`, `handleClient` runs each client in an independent coroutine on `Dispatchers.IO`.
  4. Multiple threads concurrently execute `stream.armWindow(position)` on the same `StreamSession` instance without any locking.
  5. While Thread A is executing:
     ```kotlin
     val iterator = deadlinePieces.iterator()
     while (iterator.hasNext()) {
       val piece = iterator.next()
       if (...) { iterator.remove() }
     }
     ```
     Thread B is executing `deadlinePieces.add(piece)`.
  6. Standard `java.util.HashSet` is not thread-safe. Concurrent modifications during iteration throw `java.util.ConcurrentModificationException` or corrupt internal node links in Java's `HashMap`, leading to infinite loops and ANR.

- **Worked Example**:
  - *Input*: User rapidly seeks forward twice on the player scrubber (e.g., from 01:00 to 05:00 and then immediately to 10:00).
  - *Observed Execution*: HTTP request 1 is still serving/arming window while HTTP request 2 calls `armWindow(600_000)` -> `ConcurrentModificationException` thrown in `StreamServer.serve()`, dropping playback stream.
  - *Expected Execution*: Window piece deadline calculations are thread-safe and isolated from concurrent seek requests.

- **Remediation Plan & Kotlin Diff**:
  Mark `armWindow` and `armMp4TailIfNeeded` with `@Synchronized` (or protect them via a dedicated lock object), and mark `lastWindowPos` as `@Volatile`.

```kotlin
// In StreamSession.kt
private val windowLock = Any()
private val deadlinePieces = HashSet<Int>()
private val tailPieces = HashSet<Int>()
@Volatile private var lastWindowPos = -1L

fun armWindow(position: Long) = synchronized(windowLock) {
  if (closed.get()) return
  if (lastWindowPos >= 0 && abs(position - lastWindowPos) < pieceLength) return
  lastWindowPos = position

  val first = pieceAt(position)
  val last = min(numPieces - 1, pieceAt(position + READ_AHEAD_BYTES))

  for (piece in first..last) {
    if (deadlinePieces.add(piece)) {
      val deadlineMs = ((piece - first) * 200).coerceAtLeast(0)
      runCatching { handle.setPieceDeadline(piece, deadlineMs) }
    }
  }

  val iterator = deadlinePieces.iterator()
  while (iterator.hasNext()) {
    val piece = iterator.next()
    if ((piece < first - 1 || piece > last) && !tailPieces.contains(piece)) {
      runCatching { handle.resetPieceDeadline(piece) }
      iterator.remove()
    }
  }
}
```

- **Verification Strategy**:
  - Instrumented test in `PlaybackPreparationTest.kt` launching 20 concurrent coroutines calling `armWindow(i * 10000L)` on a shared `StreamSession`. Assert zero exceptions.

### BUG-004: Synchronous SQLite Disk I/O on Android Main Thread in PlaybackController
- **Category**: Main Thread Concurrency / UI Performance (Jank & ANR)
- **Severity**: High (P1) — UI freezing, frame drops, and potential ANR during audio playback.
- **Source Location**: `app/src/main/java/com/example/audiotorrent/playback/PlaybackController.kt`: Lines 160–163, 175–185, 205–215, 640–675 (`saveCurrentPosition()`)
- **Root-Cause Analysis**:
  1. `PlaybackController` manages player state on `scope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)`.
  2. Every 3500 ms (in the periodic UI ticker: `if (ticks % 10 == 0 && player.isPlaying)`), and on every player state transition (`onIsPlayingChanged`, `onPlaybackStateChanged`, `pause()`, `stop()`), it invokes `saveCurrentPosition()`.
  3. `saveCurrentPosition()` calls:
     ```kotlin
     database.savePlaybackPosition(hash, index, pos, durationMs)
     database.recordPlaybackHistory(hash, index, fileName, pos, durationMs)
     ```
  4. In `TorrentDatabase.kt` (lines 527, 710), these methods execute `writableDatabase.insertWithOnConflict(...)` and `writableDatabase.update(...)` directly.
  5. SQLite writes require filesystem `fsync()` to ensure transaction durability in rollback journal mode. On physical flash storage (e.g. eMMC / UFS on Xiaomi selene), `fsync()` blocks the calling thread for 20–150 ms.
  6. Furthermore, if a background IO transaction (such as `ReadAlongStore.attach()` or `TorrentEngine.refresh()`) is currently holding a write lock on `TorrentDatabase`, the main thread blocks indefinitely until the background transaction commits, triggering a platform ANR dialog.

- **Worked Example**:
  - *Input*: Audio track is actively playing while an EPUB document is being imported into `ReadAlongStore`.
  - *Observed Execution*: The 3.5s position save fires on `Dispatchers.Main`. `writableDatabase` is locked by `ReadAlongStore.attach()`. Main thread freezes for 600 ms -> UI stutter, drop frames in Compose, logcat warning: `Skipped 36 frames! The application may be doing too much work on its main thread.`
  - *Expected Execution*: Main thread delegates database persistence to `Dispatchers.IO` with debouncing, never blocking UI rendering.

- **Remediation Plan & Kotlin Diff**:
  Execute `saveCurrentPosition()` asynchronously on `Dispatchers.IO` using a non-blocking background launch, and avoid redundant writes if the position has not changed significantly.

```kotlin
// In PlaybackController.kt
private var lastSavedPositionMs = -1L

private fun saveCurrentPosition() {
  val hash = currentInfoHash ?: return
  val index = currentFileIndex
  if (index < 0) return
  val pos = player.currentPosition
  val duration = player.duration
  val durationMs = if (duration > 0 && duration != C.TIME_UNSET) duration else 0L
  if (pos <= 0L || kotlin.math.abs(pos - lastSavedPositionMs) < 1000L) return
  lastSavedPositionMs = pos

  val fileName = currentSubtitle.ifBlank { "Chapter ${index + 1}" }
  scope.launch(Dispatchers.IO) {
    database.savePlaybackPosition(hash, index, pos, durationMs)
    database.recordPlaybackHistory(hash, index, fileName, pos, durationMs)
  }
}
```

- **Verification Strategy**:
  - Run StrictMode with `detectDiskReads()` and `detectDiskWrites()` enabled in `MainActivity.onCreate()`. Verify zero StrictMode disk violation penalties during playback.

### BUG-005: Unhandled MediaCodec Release Exception Leaking Stream Lease in AudioWindowDecoder
- **Category**: Resource Leak / Lifecycle
- **Severity**: Medium-High (P1) — Active stream lease reference count permanently leaked, preventing lease cleanup.
- **Source Location**:
  - `app/src/main/java/com/example/audiotorrent/data/lyrics/AudioWindowDecoder.kt`: Lines 100–106
  - `app/src/main/java/com/example/audiotorrent/torrent/TorrentEngine.kt`: Lines 405–430 (`analysisDataSource()`)
- **Root-Cause Analysis**:
  1. `AudioWindowDecoder.decode` manages `MediaCodec`, `MediaExtractor`, and `source = dataSource(track)`.
  2. In the `finally` block:
     ```kotlin
     } finally {
       codec?.let { runCatching { it.stop() }; it.release() }
       extractor.release()
       source.close()
     }
     ```
  3. Notice that `it.stop()` is wrapped in `runCatching`, but `it.release()` is NOT.
  4. If `MediaCodec` encounters a native hardware error or illegal state, calling `it.release()` can throw an unhandled `IllegalStateException`.
  5. When `it.release()` throws, execution jumps out of the `finally` block before `extractor.release()` and `source.close()` are called.
  6. `source` is the `MediaDataSource` created in `TorrentEngine.analysisDataSource()` which acquired a reference count on `stream` (`current.retain()`). Its `close()` method calls `releaseStream(stream)`.
  7. Because `source.close()` is never invoked, `stream.referenceCount` remains >= 1 forever. `activeStream` cannot be closed or prioritized for offline downloading, leaking file descriptors and swarm piece priorities.

- **Worked Example**:
  - *Input*: MediaCodec fails to decode a corrupt AAC audio frame in an MP4 file.
  - *Observed Execution*: Decoder aborts. `it.release()` throws `IllegalStateException`. `source.close()` is skipped -> `StreamSession.refs` remains 1 -> Stream lease remains locked forever.
  - *Expected Execution*: All resources (`codec`, `extractor`, `source`) are guaranteed to close independently via isolated `runCatching` blocks.

- **Remediation Plan & Kotlin Diff**:
```kotlin
// In AudioWindowDecoder.kt
} finally {
  codec?.let {
    runCatching { it.stop() }
    runCatching { it.release() }
  }
  runCatching { extractor.release() }
  runCatching { source.close() }
}
```

- **Verification Strategy**:
  - Unit test in `AutomaticBookTextTest.kt` simulating a decoder failure and asserting that `source.close()` is invoked and `stream.referenceCount` decrements to 0.

### BUG-006: Regex Greedy Match & Bitrate False-Positive in AudioBookAligner
- **Category**: Functional / Text Alignment Anomaly
- **Severity**: Medium (P2) — Completely breaks chapter-to-track alignment for standard audiobook filenames containing bitrates or years.
- **Source Location**: `app/src/main/java/com/example/audiotorrent/data/lyrics/AudioBookAligner.kt`: Lines 92–97 (`extractLeadingOrIsolatedNumber()`)
- **Root-Cause Analysis**:
  1. The chapter extraction regex is defined as:
     ```kotlin
     val regex = Regex("(?:chapter|ch|track|part|cd)?\\s*0*(\\d+)", RegexOption.IGNORE_CASE)
     ```
  2. Notice that the prefix `(?:chapter|ch|track|part|cd)?` is OPTIONAL (`?`).
  3. `regex.find(text)` searches for the FIRST matching pattern anywhere in `text`.
  4. For an audiobook file named `"Pride and Prejudice - 192kbps - Chapter 01.mp3"`, the regex finds `"192"` (from `192kbps`) before it ever reaches `"Chapter 01"`, returning `192`.
  5. For an audiobook named `"1984 - Ch. 01.mp3"`, it returns `1984`.
  6. In `AudioBookAligner.align()`, `audioNum` is extracted as 192, while the EPUB chapter number is 1. The numbers do not match (`chapterNumberMap[192]` is null).
  7. High-confidence `EXACT_TITLE_MATCH` fails, and the aligner falls back to lower-confidence proportional guessing, misaligning text sentences against playback timestamps.

- **Worked Example**:
  - *Input*: Audio files: `["Book - 64kbps - Chapter 01.mp3", "Book - 64kbps - Chapter 02.mp3"]`. EPUB chapters: `["Chapter 1", "Chapter 2"]`.
  - *Observed Output*: `extractLeadingOrIsolatedNumber` returns `64` for all files. 0 matches found in `chapterNumberMap`. Fallback to `PROPORTIONAL` with 0.60 confidence.
  - *Expected Output*: Explicit keyword `"Chapter 01"` takes precedence over bitrate `64kbps`. Match returns 1 and 2 with 1.0 confidence.

- **Remediation Plan & Kotlin Diff**:
  Match explicit chapter/track keyword prefixes first. Only if no keyword prefix exists, fall back to leading numbers, explicitly excluding bitrates (e.g. `128kbps`, `64kbps`) and four-digit years.

```kotlin
// In AudioBookAligner.kt
fun extractLeadingOrIsolatedNumber(text: String): Int? {
  // 1. Explicit keyword match takes top priority: e.g. "Chapter 01", "Track 2", "Ch. 5"
  val explicitRegex = Regex("\\b(?:chapter|ch|track|part|cd|disc)[\\s_.-]*0*(\\d+)\\b", RegexOption.IGNORE_CASE)
  explicitRegex.find(text)?.let {
    return it.groupValues[1].toIntOrNull()
  }

  // 2. Clean out bitrate tags like 64kbps, 128kbps, 192kbps, 320kbps
  val cleanText = text.replace(Regex("(?i)\\b\\d{2,3}\\s*kbps\\b"), "")

  // 3. Match leading numbers at the start of filename (e.g. "01 - Title.mp3", "[02] Title.mp3")
  val leadingRegex = Regex("^(?:\\[|\\()?0*(\\d{1,3})(?:[\\])]|[\\s._-])")
  leadingRegex.find(cleanText.trim())?.let {
    return it.groupValues[1].toIntOrNull()
  }

  // 4. Standalone isolated number (excluding 4-digit years 1900-2099)
  val isolatedRegex = Regex("\\b0*(\\d{1,3})\\b")
  return isolatedRegex.find(cleanText)?.groupValues?.get(1)?.toIntOrNull()
}
```

- **Verification Strategy**:
  - Unit test in `EpubAndAlignmentTest.kt` asserting that `"Pride and Prejudice - 192kbps - Chapter 01.mp3"` resolves to chapter `1`.

### BUG-007: JNI Modified UTF-8 Vulnerability in whisper_jni.cpp
- **Category**: Native Memory / JNI Crash
- **Severity**: Medium-High (P1) — Process termination via `SIGABRT` if Whisper emits non-BMP characters or invalid UTF-8 bytes.
- **Source Location**: `app/src/main/cpp/whisper_jni.cpp`: Lines 62–67
- **Root-Cause Analysis**:
  1. In `Java_com_example_audiotorrent_data_lyrics_WhisperEngine_nativeTranscribe`:
     ```cpp
     for (int i = 0; i < count; ++i) {
         auto text = env->NewStringUTF(whisper_full_get_segment_text(engine->context, i));
         ...
     }
     ```
  2. `whisper_full_get_segment_text` outputs standard UTF-8 string data from the speech model.
  3. `env->NewStringUTF(const char* bytes)` in JNI does NOT accept standard UTF-8; it strictly requires **Modified UTF-8** (RFC 2279 variant where 4-byte code points > U+FFFF are encoded as surrogate pairs, and `0x00` is encoded as `0xC0 0x80`).
  4. If the Whisper model outputs any non-BMP code point (e.g., supplementary symbols, musical notation `♪` when transcribed as supplementary characters, or emojis) or an incomplete byte sequence, Android ART's JNI check terminates the process with:
     `JNI DETECTED ERROR IN APPLICATION: input is not valid Modified UTF-8: illegal start byte 0xf0...`

- **Worked Example**:
  - *Input*: Narration audio contains a musical interlude or special unicode quote, causing Whisper to decode a character with code point > U+FFFF (`0xF0 0x9F...`).
  - *Observed Execution*: ART's CheckJNI / UTF-8 validator fails in `NewStringUTF` -> Process aborts with SIGABRT.
  - *Expected Execution*: Text is validated and converted into valid Modified UTF-8 / UTF-16 before JNI string allocation.

- **Remediation Plan & C++ Diff**:
  Sanitize the UTF-8 buffer or convert valid UTF-8 to UTF-16 (`jcharArray` / `NewString`) before returning to the JVM.

```cpp
// In whisper_jni.cpp
static jstring safeNewStringUTF(JNIEnv *env, const char *str) {
    if (!str) return env->NewStringUTF("");
    // Check if string contains valid Modified UTF-8, replace invalid bytes
    std::string safe;
    const unsigned char *p = reinterpret_cast<const unsigned char *>(str);
    while (*p) {
        if (*p < 0x80) {
            safe.push_back(*p++);
        } else if ((*p & 0xE0) == 0xC0 && (p[1] & 0xC0) == 0x80) {
            safe.push_back(*p++); safe.push_back(*p++);
        } else if ((*p & 0xF0) == 0xE0 && (p[1] & 0xC0) == 0x80 && (p[2] & 0xC0) == 0x80) {
            safe.push_back(*p++); safe.push_back(*p++); safe.push_back(*p++);
        } else if ((*p & 0xF8) == 0xF0 && (p[1] & 0xC0) == 0x80 && (p[2] & 0xC0) == 0x80 && (p[3] & 0xC0) == 0x80) {
            // Convert 4-byte standard UTF-8 sequence to surrogate pair for Modified UTF-8
            uint32_t cp = ((*p & 0x07) << 18) | ((p[1] & 0x3F) << 12) | ((p[2] & 0x3F) << 6) | (p[3] & 0x3F);
            p += 4;
            cp -= 0x10000;
            uint16_t high = 0xD800 + (cp >> 10);
            uint16_t low = 0xDC00 + (cp & 0x3FF);
            safe.push_back(0xE0 | (high >> 12));
            safe.push_back(0x80 | ((high >> 6) & 0x3F));
            safe.push_back(0x80 | (high & 0x3F));
            safe.push_back(0xE0 | (low >> 12));
            safe.push_back(0x80 | ((low >> 6) & 0x3F));
            safe.push_back(0x80 | (low & 0x3F));
        } else {
            p++; // Drop invalid byte
        }
    }
    return env->NewStringUTF(safe.c_str());
}
```

### BUG-008: StreamServer Permanent Lockout After stop()
- **Category**: Concurrency / Lifecycle
- **Severity**: Medium (P2) — StreamServer cannot be restarted after being stopped.
- **Source Location**: `app/src/main/java/com/example/audiotorrent/stream/StreamServer.kt`: Lines 40–58
- **Root-Cause Analysis**:
  1. `StreamServer` manages startup state with `private val started = AtomicBoolean(false)`.
  2. In `start()`:
     ```kotlin
     if (started.compareAndSet(false, true)) { ... }
     ```
  3. In `stop()`:
     ```kotlin
     fun stop() {
       runCatching { serverSocket?.close() }
       serverSocket = null
       port = 0
       scope.cancel()
     }
     ```
  4. Notice that `started.set(false)` is NEVER called in `stop()`.
  5. Furthermore, `scope.cancel()` permanently cancels the `CoroutineScope`.
  6. If `stop()` is called and the service or app subsequently attempts to restart playback via `start()`, `started.compareAndSet(false, true)` returns `false`. `start()` returns `0`, and the loopback stream server is permanently dead until process restart.

- **Worked Example**:
  - *Input*: Playback is stopped via `playback.stop()`, and the user later presses Play on another book.
  - *Observed Execution*: `streamServer.start()` returns 0. ExoPlayer fails to connect to `http://127.0.0.1:0/...` with `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED`.
  - *Expected Execution*: `start()` cleanly rebinds a new socket and coroutine scope if previously stopped.

- **Remediation Plan & Kotlin Diff**:
```kotlin
// In StreamServer.kt
@Volatile private var scope = CoroutineScope(SupervisorJob() + Dispatchers.IO)

fun start(): Int {
  if (started.compareAndSet(false, true)) {
    try {
      if (!scope.isActive) scope = CoroutineScope(SupervisorJob() + Dispatchers.IO)
      val socket = ServerSocket(0, 50, InetAddress.getByName("127.0.0.1"))
      serverSocket = socket
      port = socket.localPort
      scope.launch { acceptLoop(socket) }
    } catch (_: Throwable) {
      started.set(false)
      port = 0
    }
  }
  return port
}

fun stop() {
  runCatching { serverSocket?.close() }
  serverSocket = null
  port = 0
  scope.cancel()
  started.set(false)
}
```

- **Verification Strategy**:
  - Unit test in `StabilizationAndArchitectureTest.kt` executing `server.start() -> server.stop() -> server.start()`. Assert non-zero port and valid HTTP response.

### BUG-009: SQLite CursorWindow 2MB Row Limit Crash on Large EPUB/TXT Chapters
- **Category**: Persistence / Android Platform Limits
- **Severity**: High (P1) — Crash with `SQLiteBlobTooBigException` when querying books with large chapters.
- **Source Locations**:
  - `app/src/main/java/com/example/audiotorrent/data/lyrics/ReadAlongStore.kt`: Lines 22–35, 41–47 (`attach()`, `book()`)
  - `app/src/main/java/com/example/audiotorrent/data/lyrics/EpubExtractor.kt`: Lines 45–60 (`parseTextIntoChapters()`)
- **Root-Cause Analysis**:
  1. `ReadAlongStore.attach` writes `chapter.text` into the `content` column of the `readalong_chapters` SQLite table.
  2. For large single-file EPUBs or `.txt` imports without explicit chapter headings (e.g. *The Count of Monte Cristo* or *War and Peace*), `EpubExtractor.parseTextIntoChapters` falls back to creating a single `EpubChapter` with the entire book's text.
  3. When `chapter.text` exceeds ~1.5–2.0 MB (approximately 300,000 words), Android's `CursorWindow` (which has a hard limit of 2 MB on API < 34 and 4 MB on API 34+) cannot load the row.
  4. When `ReadAlongStore.book(track)` executes:
     ```kotlin
     val chapters = db.query("readalong_chapters", null, "book_id=?", ...).use { ... }
     ```
     Android ART throws `android.database.sqlite.SQLiteBlobTooBigException: Row too big to fit into CursorWindow requiredPos=0, totalRows=1`.
  5. The companion text can never be loaded again, leaving the book stuck in `ReadAlongPhase.ERROR`.

- **Worked Example**:
  - *Input*: User imports a 3 MB `.txt` transcript or a single-HTML-spine EPUB.
  - *Observed Execution*: Import succeeds, but subsequent `store.book(track)` crashes on `db.query` with `SQLiteBlobTooBigException`.
  - *Expected Execution*: Large chapters are chunked or stored on the internal filesystem, ensuring all SQLite rows fit well within `CursorWindow` limits.

- **Remediation Plan & Kotlin Diff**:
  1. In `EpubExtractor.parseTextIntoChapters`, split any text chunk larger than 250,000 characters into sub-chapters on paragraph boundaries (`\n\n`).
  2. In `EpubStructureParser`, if any extracted XHTML chapter exceeds 250,000 characters, automatically split it into sequenced sub-chapters.

```kotlin
// In EpubExtractor.kt
private const val MAX_CHAPTER_CHARS = 200_000

fun parseTextIntoChapters(text: String): List<EpubChapter> {
  val clean = text.trim()
  if (clean.isBlank()) return emptyList()

  val rawChapters = parseRawChapters(clean)
  return rawChapters.flatMap { ch ->
    if (ch.text.length <= MAX_CHAPTER_CHARS) listOf(ch)
    else chunkLargeChapter(ch)
  }
}

private fun chunkLargeChapter(chapter: EpubChapter): List<EpubChapter> {
  val paragraphs = chapter.text.split(Regex("(?<=\\n\\n)"))
  val chunks = mutableListOf<EpubChapter>()
  val current = StringBuilder()
  var part = 1

  for (p in paragraphs) {
    if (current.length + p.length > MAX_CHAPTER_CHARS && current.isNotEmpty()) {
      val str = current.toString().trim()
      chunks.add(EpubChapter(
        index = chapter.index * 100 + part,
        id = "${chapter.id}_part$part",
        href = "${chapter.href}#part$part",
        title = "${chapter.title} (Part $part)",
        text = str,
        wordCount = str.split(Regex("\\s+")).count { it.isNotBlank() }
      ))
      current.clear()
      part++
    }
    current.append(p)
  }
  if (current.isNotEmpty()) {
    val str = current.toString().trim()
    chunks.add(EpubChapter(
      index = chapter.index * 100 + part,
      id = "${chapter.id}_part$part",
      href = "${chapter.href}#part$part",
      title = "${chapter.title} (Part $part)",
      text = str,
      wordCount = str.split(Regex("\\s+")).count { it.isNotBlank() }
    ))
  }
  return chunks
}
```

- **Verification Strategy**:
  - Unit test in `EpubAndAlignmentTest.kt` passing a 3.5 MB synthetic book text into `EpubExtractor.extractBookFromBytes` and reading it through `ReadAlongStore.attach()` and `ReadAlongStore.book()`. Assert clean return and zero `SQLiteBlobTooBigException`.

### BUG-010: "Replace Edition" Search Dialog Dismissal Race in LyricsView
- **Category**: UI / State Synchronization
- **Severity**: Medium (P2) — User cannot replace an attached ebook edition while audio is playing.
- **Source Location**: `app/src/main/java/com/example/audiotorrent/ui/player/LyricsView.kt`: Lines 142–146
- **Root-Cause Analysis**:
  1. In `LyricsView.kt`:
     ```kotlin
     val findText = { showSearch = true; search() }
     ```
     When the user opens the Text Options dropdown and taps "Replace edition", `findText()` sets `showSearch = true` and invokes `search()`.
  2. However, line 145 contains an over-aggressive `LaunchedEffect`:
     ```kotlin
     LaunchedEffect(state.track, state.phase, state.bookId, cleanBookTitle, searchAuthor, bookIdentityReady, bookIdentityTrack, isVisible) {
       if (bookIdentityReady && isVisible) repository.ensureBookText(...)
       if (state.bookId != null && state.phase != ReadAlongPhase.LOADING && !state.searching) showSearch = false
     }
     ```
  3. When `state.bookId != null` (an edition is already attached) and audio is playing:
     Whenever `state.phase` pulses between `PREPARING` and `READY`, or before `state.searching` transitions to true (or as soon as search results arrive), the `LaunchedEffect` executes:
     `showSearch = false`!
  4. The search UI / edition replacement dialog is abruptly closed right in front of the user.

- **Worked Example**:
  - *Input*: User is reading Pride and Prejudice and decides to select another edition via "Replace edition".
  - *Observed Execution*: Dropdown opens, user taps "Replace edition". The search sheet flashes open for 50 ms and instantly vanishes.
  - *Expected Execution*: The search sheet stays open until the user chooses a replacement edition or explicitly dismisses it.

- **Remediation Plan & Kotlin Diff**:
  Differentiate user-requested search from automatic background lookup, and only close `showSearch` when a new edition is explicitly chosen or cancelled.

```kotlin
// In LyricsView.kt
var userOpenedSearch by rememberSaveable(state.track) { mutableStateOf(false) }

val findText = {
  userOpenedSearch = true
  showSearch = true

LaunchedEffect(state.track, state.phase, state.bookId, cleanBookTitle, searchAuthor, bookIdentityReady, bookIdentityTrack, isVisible) {
  if (bookIdentityReady && isVisible) repository.ensureBookText(BookIdentity(cleanBookTitle, searchAuthor), selectedTracks, bookIdentityTrack ?: state.track)
  // Only auto-dismiss search if the search was NOT explicitly opened by the user
  if (!userOpenedSearch && state.bookId != null && state.phase != ReadAlongPhase.LOADING && !state.searching) {
    showSearch = false
  }
}
```

| **Phase 4** | **P3 (Normal)** | BUG-010, UI Mojibake | `LyricsView`, `PlayerScreen`, `LibraryScreen`, `TorrentScreen` | Fix "Replace Edition" dismissal race and restore clean UTF-8 typography across UI screens. |
